# C-06 inbox delivery

Worker implementation in batch 007. On by default. This is separate from inbox reading, acknowledgement, quota continuation, and the internal initial automation `queued_prompt`. Sending or reading mail cannot change the policy. No MCP tool configures it and no additional controller capability is granted. Messages from external controllers never wake a session.

A session with no saved policy wakes on new peer messages: standing, no total-turn cap, 30-second cooldown and five messages per batch. No policy row is written until its first mail is dispatched, and the policy reports generation 0 with the reason `On by default`. Sessions a human configured keep their saved choice, including off.

The human opens the session's Agents & inbox dialog to set limits or disable automatic turns. The form starts from the saved policy. In a `PUT`, **No total-turn cap** is never inferred from missing input. The form's default cooldown/debounce is 30 seconds and batch size is five messages. Required bounds remain 5–3600 seconds and 1–10 messages per batch. A finite cap accepts 1–20 submission attempts; an optional absolute stop time must be within 24 hours. Legacy finite deadlines and caps retain their original meaning and expire normally. Turn counts bound submission attempts, not dollars or tokens.

Only the human ends an authorization: by disabling it, or when a stop time or total-turn cap they chose runs out (incomplete legacy bounds also end it). A default policy has no authorization to revoke: host-driven cancellation (a remote disconnect during a turn, or the directory leaving the allowed roots) drops its queued batch and leaves it on. Everything else holds or adapts. Authorization survives service restarts. It follows the session to its current project, native context ID and directory at the next dispatch, rather than being bound to the values at authorization time. While the session cannot take a turn, queued mail is held (within the pending cap) and delivered once it can; `GET` reports the reason as `held`. Hold reasons: archived, explicitly suspended, storage error latch, error/closed status, no project, no native context, waiting for resume, communication grant off, local directory unavailable, native session not attached, and (remote) host or directory unavailable. The inbox scheduler never launches a provider or replaces a native context. An identical configuration request ID never resets a counter or re-enables a cancelled policy; different payload reuse returns 409. Browser retries after an ambiguous failure retain the request ID and payload.

Only messages sent while the policy is enabled enroll. There are at most 20 pending messages. Overflow remains in the manual mailbox and receives a cancelled delivery record. Automatic delivery never advances a manual cursor. When the native turn starts (`begin` passes), messages quoted in full are acknowledged: they are in the agent's context. Truncated messages stay unacknowledged until the agent fetches them with `read_message`; a wake that is cancelled or fails before the turn starts acknowledges nothing. Acknowledging a message (MCP `acknowledge_message`, MCP `read_message` of a received message, the browser's per-message button or **Acknowledge all**) drops its queued wake. Existing sender-scoped send idempotency is unchanged; enrollment commits in that same transaction. Batches wait at least the cooldown after the oldest queued message, and after the preceding dispatch. Busy/approval states coalesce queued mail rather than starting concurrent work.

Senders must still be live communicating peers in the recipient's current project at dispatch; mail from a sender that can no longer message (grant revoked, moved project, deleted) is dropped from the queue and the rest of the batch still wakes. Roots, native attachment, lifecycle, quota pause, storage, approvals, service admission and human-input priority are checked before claiming. There is no native resume or new context fallback. Peer messages are JSON quoted, attributed by sender ID/title/message ID, and explicitly labelled untrusted data that cannot expand authorization. Each wake includes at most the first 256 characters of each message and 80 characters of the sender title. Full messages remain in the mailbox.

Explicit Stop interrupts an in-flight automatic turn and drops queued wakes (the messages stay in the inbox) but keeps the authorization, so later messages wake the session again. Archive does the same, and archived sessions reject new messages (409), so they keep old mail but receive nothing until unarchived. Suspend and a dropped remote host interrupt an in-flight automatic turn and hold queued wakes. Completion reports neither revoke nor interrupt. Deadline, exhausted turn bounds and human disable cancel the authorization and request cancellation of an automatic native turn already in flight; unrelated human turns are left to their normal lifecycle controls. Cancellation uses existing runtime cancellation/grace handling. A verified quota rejection during an inbox turn clears its automatic quota timer and visibly pauses while retaining quota policy authorization/evidence: a separate quota policy cannot expand the inbox turn budget. Human status-check behavior is untouched. A normal transport turn ending resolves submission uncertainty; it does not assert task completion.

SQLite schema version 7 adds only `inbox_policies`, `inbox_policy_requests`, `inbox_deliveries` and an index. Policy generations and per-message queued/claimed/sent/paused/cancelled states persist. The derived `inbox:<recipient>:<generation>:<attempt>` request and claim are FULL-synchronous committed before the existing native Prompt command. A failed/uncertain submission is paused and never retried. Startup pauses unresolved claimed/sent records for inspection and never replays them, while preserving valid authorization, its generation, counters and cooldown. Unclaimed queued messages remain queued; dispatch waits for the same context to attach and all normal gates to pass. A paused uncertain message is never automatically re-enrolled, even after reauthorization. Only incomplete or expired saved bounds cancel queued work at startup. Missing legacy bound fields are treated as expired/exhausted, never as permission for unlimited work. Deleting a recipient cascades its policy/ledger; existing message provenance remains.

Browser API: `GET /api/sessions/{id}/inbox-delivery` returns policy, pending count, and up to 40 recent ledger records. `PUT` accepts `{enabled, requestId, deadline?, maxTurns?, unlimitedTurns?, cooldownSeconds, maxBatch}` (milliseconds UTC deadline). Omitted/null `deadline` means standing authorization. An enabled policy requires either `maxTurns:1..20` with `unlimitedTurns:false` (or omitted), or explicit `unlimitedTurns:true` with omitted/null `maxTurns`. Specifying both an unlimited choice and a finite cap is rejected. GET returns null for standing `deadline` or uncapped `maxTurns`. Cooldown and batch size remain required. Disable only needs `{enabled:false, requestId}`. Browser controls live in `web/inbox-delivery.js`, with readable wrapping, labels, status announcement, and 44px controls on phones. The existing same-user/browser trust boundary documented in AGENT-COMMUNICATION.md applies; this is not isolation against a malicious same-OS-user process.

Integration hooks:

- `inbox_delivery::enqueue(tx, recipient, message_id)` in communication send transaction.
- Startup `reconcile(&mut store)` before session restore; scheduler starts beside quota scheduler.
- `dispatch_one(app, session, human_pending)` runs under communication → run → workspace locks and uses existing session request serialization and the same native Prompt RPC through `Command::InboxPrompt`.
- `explicit_input_pending(session)` now checks both the internal initial prompt and L-05 durable pending/error items without consuming or reclassifying them. Combined acceptance verifies FIFO human input priority, paused queue blocking, deliberate resume and quota/status-probe gates.
- Runtime termination calls `finished(session, exact_owner)` once before idle; ordinary human turns pass no inbox owner. Stop calls `stop`, which keeps the policy. Archive calls `stop`; Suspend and remote disconnect call `interrupt_inflight`; project, grant and deletion hooks call `drop_from_sender`. `service_restart::Manager::block_admission_for_test` exists only under cfg(test).

Checks (demo only, no paid inference): `cargo test --locked --offline`; `cargo build --locked --offline`; `node scripts/inbox-delivery-smoke.mjs`. The smoke suite uses isolated `/tmp/agentworks-inbox-*` state and assigned port 4501 (override within 4501–4505), never live 4318. ## Reply requests

`send_message` accepts `expectReply: true`. The first message the recipient sends back with `replyTo` set to that message wakes the requesting session once, through this same delivery path, whether or not it has a standing inbox authorization. The reply is the requester's own authorization: it asked to be woken by exactly that message.

- Only a session that sent the request can be woken, only by a peer session reply, and only by the first reply. Later replies and replies to messages without `expectReply` are ordinary mail.
- Without a standing policy, reply wakes use a 5-second cooldown and at most 5 messages per turn; human input still takes priority and every hold applies.
- Disabling, replacing or expiring a standing policy leaves queued reply wakes in place. Stop and archive drop them like any queued wake.
- `read_inbox`, `read_message` and the browser inbox show `expectReply` and `replyId` (awaiting or answered).
- Requests are stored in the additive `reply_requests` table (no schema version change).

## Turn ownership and storage failures

Historical claimed/sent rows and reason strings do not identify the active turn. The runtime persists an exact `inbox_turn` token (request ID, generation, native context ID) in session state and carries it in `InboxPrompt` / `CancelInbox` commands. The runtime independently matches cancellation against its local active token; idle, human, other-request, other-generation and other-native turns ignore a late targeted cancellation. Terminal lifecycle status and ordinary human/initial prompt admission clear ownership. Native admission rechecks ownership and rejects revocation before the queued command reaches the native RPC. Exact completion clears only its own token and ledger batch; stale callbacks and human completions cannot touch another turn or its quota state. A fast completion closes its claimed batch before submit bookkeeping can run, and conditional bookkeeping cannot reopen it.

Finish/claim/event-write failure tests inject SQLite failures. The process latches admission closed (a hold until restart), issues only an exact targeted cancellation, and persists the paused ledger batch where writes remain possible. The authorization itself is kept. When storage is entirely unavailable, the already durable claim is retained and startup never replays it. Restore clears quota timers bound to a persisted inbox owner while retaining quota policy/evidence; unrelated human quota schedules are preserved. Project deletion serializes communication → run → workspace, and releases store/catalog guards before session/revocation callbacks. Reassignment releases catalog before callbacks. Completion reports commit and drop their store guard before interrupting an exact active owner. Concurrent finish versus reassign/delete/completion tests exercise these paths with a five-second failure bound. Schema version remains 7; this review adds only a backward-compatible session JSON ownership field.
