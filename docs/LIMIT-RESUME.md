# L-09 — Resume when usage limits reset

Implemented as an opt-in Rust/SQLite session continuation timer. It does not restart the server and introduces no workflow engine or queued-input system.

New and existing sessions default **off**. The new-session checkbox and composer’s “Usage-limit continuation” details authorize three attempts within 24 hours. The existing-session advanced bounds controls and human API can explicitly choose 1–100 attempts and an absolute millisecond deadline within 30 days. These bounds, consumed attempts, policy origin and inherited parent authorization are persisted. Enabling is a deliberate new human authorization; it never revives a cancelled timer by itself. Disabling removes the timer. A human may choose a local manual time on a limited pause or resume deliberately now. The composer shows origin, attempts/deadline, reason, reset source, observation time and a countdown computed locally from the saved absolute due time; there are no per-second server broadcasts or status requests.

## Trustworthy provider paths

Inspected installed versions: Claude ACP 0.93.0 and Codex ACP 2.2.2.

- **Claude:** the adapter's `rate_limit_event` forwards `usage_update._meta['_claude/rateLimit']` only after assistant token usage is known. The SDK `SDKRateLimitInfo` has `status`, `resetsAt` (Unix seconds), `overageStatus`, and `overageResetsAt`. Only `status: rejected` counts. A first-turn prompt error with exact `data.errorKind: rate_limit` also produces a trusted unknown-reset pause when the adapter suppresses its usage notification. All rejected observations in the active turn are combined; rejected overage and base windows require the later reset. Any unknown blocking reset makes the overall reset unknown. A subsequent normal successful turn response cancels this evidence rather than scheduling another turn. A quota observation followed by an error/refusal is eligible after the response terminates.
- **Codex:** the installed adapter handles native account reset updates internally for `/status`, but ACP `usage_update` contains context token counts without reset timestamps. Its prompt errors preserve exact `data.codexErrorInfo` values `usageLimitExceeded` / `rateLimitExceeded`. These exact transport errors trigger a bounded read-only `codex app-server` connection: `initialize`, `initialized`, then `account/rateLimits/read`. It creates no thread, session or model turn. Latest future reset across exhausted primary/secondary (`usedPercent >= 100`) and individual (`remainingPercent <= 0`) windows is used conservatively across returned limit IDs. Missing/stale data, a spend-control block, failed read, API-key mode or no exhausted window leaves a manual pause. The subprocess is killed on completion/timeout, has an eight-second timeout and 128 KiB total stdout bound, ignores stderr, and stores only the selected reset and constant source/reason strings. It uses the existing sign-in; credentials are never copied into timer state. `AGENTWORKS_CODEX_QUOTA_PATH` can select the executable for deterministic protocol fixtures. Quota errors that the adapter reduces solely to assistant prose cannot authorize a timer. No `/status` prompt or text scraping is used.
- **OpenCode:** no verified reset transport in this slice; automatic detection is unsupported. Its arbitrary error prose is never interpreted as quota evidence. Existing manual session/prompt controls remain available.
- **Demo:** explicit `quota known`, `quota unknown`, `quota multi`, `quota repeat`, `quota known recovered`, and `quota generic` fixtures exercise structured limits, missing/later resets, repeated bounds, successful recovery and injected prose without inference.

Generic tools, inbox messages, assistant text, authentication, network, timeout and context errors cannot create a timer. Unknown or stale reset information never produces a guessed countdown. Repeated attempts use at least exponential backoff (1–256 seconds), respect the reported reset, and retain the saved attempt/deadline bound. A provider reset beyond that deadline is shown as blocked rather than scheduled.

## Terminal and human boundaries

The implementation does **not** infer task completion or “stop after this round” from natural-language prose. Assigned scope and stop instructions stay in the original native conversation. An ordinary successful ACP turn ending schedules no further work. Explicit Stop (including when idle), disabling, deletion, newer accepted replacement-work human/controller input, cancellation, and an explicit `report_completion` (completed or blocked) cancel pending work. Stop and completion reports end the policy authorization; ordinary turn completion cancels the timer while retaining the human policy for future quota failures. Browser disconnect does not cancel a durable timer. The deliberate manual-resume action disables the old authorization and submits a new attributed instruction with a stable retry ID.

## Read-only status checks (B-02)

Exact `/status` on Codex and `/usage` on Claude preserve a paused assignment's continuation. The command must also be advertised by the current adapter with no argument input. Surrounding whitespace is accepted; arguments, prefixes, other slash commands, skills, OpenCode commands and ordinary model work use the existing replacement-work cancellation behavior. Claude `/status` is not exempted: this slice verifies the adapter's structured local `/usage` path only. Demo advertises both commands for deterministic fixtures.

The prompt acceptance hook `continuation.begin_turn(provider, commands, text)` records a durable local-read purpose with the current generation and authorization. It retains the original limited assignment, native context, reset source/time, absolute deadline and consumed/remaining attempts in place. A successful check is not assignment completion, and does not enable policy or reset counters. Fresh structured rejection evidence can extend a known reset or supply a previously unknown reset within the existing bounds; stale or unknown check evidence retains the original reset/source rather than guessing a replacement. Reset evidence from a successful local check is usable because it describes quota, not assignment completion. A non-quota local-read error also leaves the assignment pending.

Stop, disable, policy replacement, completion, revocation and deadline/bound exhaustion retain precedence through generation/authorization checks and the existing scheduler validation. Cancellation of a check cancels its pending continuation. A timer due while a check runs remains saved and dispatches only after the existing turn/approval/storage/readiness gates permit it. Crash recovery abandons the local check without replay, then opens the saved native context for the original assignment. Existing uncertain continuation claims still pause for inspection. If a check loses its transport without a response, the eventual continuation claim clears the abandoned read purpose before dispatch.

## Durability and dispatch

Schema v6 retains every v5 table and stores continuation state in the existing transactional session-state JSON. State and audit/status events commit together under the existing data→Store lock order, with SQLite FULL synchronous durability. Policy, limits, observation/source, timer generation, authorization revision, native session ID, stable request/attempt IDs, claim and dispatch phase survive restart.

The scheduler serializes communication→run→workspace access. It rechecks policy and bounds, unfinished limited state, inherited parent authorization/grants/project scope, roots/harness/directory, capacity, native context, active turn, storage health and approvals. It opens only the saved native session in its original directory. Failed native resume pauses visibly and never substitutes fresh context. A timer interrupted during safe native opening can reopen; a claim or dispatch interrupted by a crash becomes **uncertain** with no automatic retry. This deliberately favors at-most-once dispatch over retrying an ambiguous provider operation. Human inspection/manual resume is required for uncertain claims, including a crash after claim but before send.

Claims and stable request IDs are committed before sending. Continuations are recorded as scheduler-attributed user turns asking the harness to inspect current task/tool results and continue only unfinished scope. They never resend the original user turn or shell command. Provider starts are staggered by at least 30 seconds per provider while the server runs, conservatively grouping all accounts without persisting account identities. Existing 12-harness capacity remains enforced. `/api/activity` separately exposes `scheduledContinuations` and `unfinishedLimitedSessions`; future timers alone do not make backed-up updates unsafe.

## MCP and human APIs

Human creation accepts `resumePolicy: {enabled, maxAttempts?, deadline?}`. `PUT /api/sessions/:id/continuation` accepts the same policy or `{enabled:true, manualDueAt:<absolute milliseconds>}` for a limited session. Session snapshots/list/activity expose effective continuation state. Existing Stop and session-resume APIs remain separate from submitting work.

Authorized MCP `start_session` has optional boolean `inheritResumePolicy` (default false). True requires an enabled, unexpired parent policy; the child inherits its remaining attempt bound and exact deadline, with persisted parent authorization linkage. It receives **no coordinator grants**. Request retries retain the same child; changed inheritance payload conflicts. At continuation dispatch every inherited ancestor must still have its original enabled authorization, live project scope and `start_sessions` grant. Normal parent turns do not revoke children; Stop, policy replacement, grant revocation, reassignment/deletion or expired authorization blocks the inherited wake. Humans may explicitly establish an independent policy without MCP grants.
