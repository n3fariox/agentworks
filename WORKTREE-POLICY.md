# Project workspace policy and worktree launches

Workspace preparation runs in the backend before starting any session harness, including demo sessions. Browser creation, MCP `start_session` and manual automation runs use the same preparation function. Existing registered sessions resume in their saved canonical cwd, regardless of later policy changes. Session deletion retains the worktree, branch and every file. Archive cleanup of worktrees created by a session is described in [work/WORKTREE-CLEANUP.md](work/WORKTREE-CLEANUP.md); merge controls are deferred.

## HTTP API

All mutations use the existing human HTTP Origin checks. Workspace policy is not exposed as an MCP mutation.

- `GET /api/projects/{id}/workspace-policy` returns `{defaultMode:"directory"|"newWorktree"|"existingWorktree",requireWorktree:boolean}`.
- `PUT /api/projects/{id}/workspace-policy` accepts and returns that object. `directory` with `requireWorktree:true` is rejected. Older catalog projects default to `directory,false`; policy is persisted as the project's `workspacePolicy` in the catalog.
- `POST /api/worktrees/list` accepts `{cwd:string}` and returns `{worktrees:[{path,branch,commit,isMain,locked,prunable}]}`. `branch` and `commit` may be null. Discovery performs bounded Git inspection only, without launching a harness or model. Paths outside effective allowed roots, unavailable paths and missing/prunable paths that cannot be canonicalized are omitted. Detached worktrees have null branch. The main checkout has `isMain:true` and cannot be selected as an existing isolated worktree.
- `POST /api/sessions` adds optional `workspace:{mode,branch?,baseRef?,path?}` and optional `requestId:string` (1–100 bytes, no control characters). Existing fields and responses remain unchanged. The response's `cwd`, `locationId` and the existing session Workspace endpoint describe the final canonical location, which is saved in session metadata and the catalog.

When `workspace` is omitted, a selected project's default is used; without a project the original directory behavior applies. Explicit workspace choices are allowed, but a requiring project validates the actual final cwd as a linked Git worktree for every provider.

For `directory`, cwd is the existing directory. It may be a linked worktree, which satisfies a requiring policy. `branch`, `baseRef` and `path` are rejected in this mode.

For `newWorktree`, cwd is a source directory within the repository. The branch defaults to a unique `agentworks/session-<uuid>` and destination to `<main-checkout-root>/.worktrees/session-<uuid>` (also when the source is itself a linked worktree, so worktrees do not nest). Optional `branch`, `baseRef` (default `HEAD`) and absolute `path` select alternatives. Base refs must resolve to a commit. Git checks out that committed revision; source uncommitted edits and untracked files are not copied. An existing destination, including an empty directory or symlink, is rejected. Existing branch names are never forced, reset or reused. Failed or interrupted operations retain any created branch, directory and files, with errors telling the caller to inspect them.

For `existingWorktree`, cwd is the selected linked worktree or a nested directory within it. Optional `path` must name an existing directory containing cwd in the same worktree; omitting it is sufficient. Main checkouts and non-Git directories are rejected. `branch` and `baseRef` are rejected.

Imports preserve their provider's original cwd rather than following a project's default creation mode. New imports first verify the supplied canonical cwd against bounded provider session discovery, then enforce the project's requirement there. A new import into a requiring project must already be in a linked worktree. Unknown histories or providers whose original cwd cannot be verified are rejected before registration; this tightens the earlier behavior where an unknown ID could register a session that subsequently failed to load. Already registered imports return their original session, and resume remains grandfathered without relocation or replacement context.

## MCP and automations

`start_session` adds the same optional `workspace` object. Project scope still comes from the caller's grants, children inherit no grants, and existing `requestId` limits remain 50 bytes. No policy-editing MCP tool is added. Manual automations follow the project's current default at execution; their saved source cwd is unchanged. A requiring `existingWorktree` default rejects an automation saved against the main checkout. Existing automation run IDs return their original session/worktree even after policy changes.

## Persistence, retries and concurrency

SQLite schema v5 adds `session_creations`, preserving v4 session/event/message/access/automation/completion data. Successful request mapping and session insertion commit together. Browser request keys, MCP actor/request keys and automation definition/run keys occupy separate namespaces. Identical retries return the original session, including after restart; changed creation payload under an existing key conflicts. Deleting a session leaves its request tombstone and subsequent retries return 410. Requests without a key remain compatible but cannot deduplicate client retries.

A request payload binding commits before preparation; a separate durable mutation marker commits immediately before any Git filesystem changes or session insertion. Mutation-free preflight failures (capacity, provider availability, missing cwd, bad ref or existing destination) can retry with the same unchanged request ID after the condition is fixed, including after restart. The original payload binding remains, so changing the payload still conflicts. Once mutation is armed, failure, process crash or future cancellation leaves that key reserved. Retrying it returns a visible conflict with the recorded error or an interruption notice and does not create another worktree. Inspect the retained repository/files and use a new request ID for a deliberate fresh attempt. Recovery does not automatically resume an incomplete checkout. Failed attempts can retain an otherwise valid worktree after a later catalog, capacity or storage error.

The async lock order is communication, automation run, workspace preparation, then short standard mutex guards. `create_session` only acquires the workspace async lock, so MCP and automation callers can retain their existing outer locks without recursive acquisition. Policy/root edits and project removal serialize with preparation. No standard mutex guard crosses a preparation await. `/api/activity` reports `workspacePreparing:true` and `safeToClose:false` while the workspace lock is held, including conservative busy reporting during short policy/root edits. RAII releases it on errors and cancellation.

## Bounds and limitations

Git subprocesses use argument arrays, null stdin, disabled hooks/fsmonitor/recursive submodule checkout, no prompts, and cleared inherited `GIT_*` repository/config overrides. Preparation never forces, resets or removes; archive cleanup is limited to session-owned worktrees (see [WORKTREE-CLEANUP.md](work/WORKTREE-CLEANUP.md)). Each subprocess has a 10-second timeout and a 256 KiB output cap; complete workspace preparation has a 12-second timeout. Existing read-only Workspace inspection retains its 3-second/16 KiB bounds. Output overflow fails explicitly; partial lists are not accepted. Import verification is capped at 100 discovery pages and 12 seconds.

Source cwd, worktree roots and Git administrative/common directories must be within effective allowed roots. Destination paths must be absolute and cannot traverse parent components or symlinks. Ancestors are checked again and the absent destination is reserved with exclusive directory creation immediately before Git mutation; canonical cwd and current roots are checked before launch. This remains same-OS-user execution: malicious concurrent filesystem replacement by another process is not eliminated by pathname checks, and Git repository configuration and tracked content remain trusted inputs. Committed credentials, if present in repository history, are ordinary tracked content; untracked credentials are not copied.

Worktrees run on their owning host using canonical per-host roots; creation, discovery, cleanup and restore share the Local implementation. File and Git views remain local only. Bare sources, non-UTF-8 Git output and unavailable provider discovery are rejected. Missing/prunable worktrees are omitted from discovery because they cannot be safely canonicalized. There is no merge, branch adoption, incomplete-checkout recovery, scheduling or paid-inference testing in this feature.
