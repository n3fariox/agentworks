# C-06 optional inbox delivery

Worker implementation in batch 007. Off by default. This is separate from inbox reading, acknowledgement, quota continuation, and the internal initial automation `queued_prompt`. Sending or reading mail cannot authorize a turn. No MCP tool enables the policy and no additional controller capability is granted.

The human opens the session's Agents & inbox dialog and explicitly authorizes automatic turns. New authorizations are standing by default: no automatic expiry, with a finite total-turn cap of one submission attempt. A human may choose **No total-turn cap**; this is never inferred from missing input. The default cooldown/debounce is 30 seconds and batch size is five messages. Required bounds remain 5–3600 seconds and 1–10 messages per batch. A finite cap accepts 1–20 submission attempts; an optional absolute stop time must be within 24 hours. Legacy finite deadlines and caps retain their original meaning and expire normally. Turn counts bound submission attempts, not dollars or tokens.

Authorization survives an ordinary service restart while the exact saved session, native provider context, project, canonical cwd and live communication grant match. It waits until that same context is attached by deliberate Resume or an already authorized supervised restart handoff. The inbox scheduler does not launch a provider or replace a native context. Identity/scope changes, unavailable cwd/native context, and incomplete saved bounds fail closed and require human reauthorization. Reauthorization is an explicit new human action. An identical configuration request ID never resets a counter or re-enables a cancelled policy; different payload reuse returns 409. Browser retries after an ambiguous failure retain the request ID and payload.

Only messages sent after authorization enroll. There are at most 20 pending messages. Overflow remains in the manual mailbox and receives a cancelled delivery record. Automatic delivery neither advances a manual cursor nor acknowledges mail. Existing sender-scoped send idempotency is unchanged; enrollment commits in that same transaction. Batches wait at least the cooldown after the oldest queued message, and after the preceding dispatch. Busy/approval states coalesce queued mail rather than starting concurrent work.

The policy binds recipient project, native provider context ID, and canonical cwd. Both peers must retain live communication grants and the same logical project at dispatch; roots, native attachment, lifecycle, quota pause, storage, approvals, service admission and human-input priority are checked before claiming. There is no native resume or new context fallback. Unavailable native context visibly disables automatic delivery and requires inspection/reauthorization. Peer messages are JSON quoted, attributed by sender ID/title/message ID, and explicitly labelled untrusted data that cannot expand authorization. Each wake includes at most the first 256 characters of each message and 80 characters of the sender title. Full messages remain in the mailbox.

Stop, Suspend, archive, grant revocation, project reassignment/deletion, session deletion, explicit completion/blocked reports, deadline and exhausted turn bounds cancel authorization. Deadline/revocation/disable also request cancellation of an automatic native turn already in flight; unrelated human turns are left to their normal lifecycle controls. Cancellation uses existing runtime cancellation/grace handling. Grant/project changes revoke pending policies that depend on the affected sender, even if restored before a dispatch tick. Completion ledger cancellation commits with the report. A verified quota rejection during an inbox turn clears its automatic quota timer and visibly pauses while retaining quota policy authorization/evidence: a separate quota policy cannot expand the inbox turn budget. Human status-check behavior is untouched. A normal transport turn ending resolves submission uncertainty; it does not assert task completion.

SQLite schema version 7 adds only `inbox_policies`, `inbox_policy_requests`, `inbox_deliveries` and an index. Policy generations and per-message queued/claimed/sent/paused/cancelled states persist. The derived `inbox:<recipient>:<generation>:<attempt>` request and claim are FULL-synchronous committed before the existing native Prompt command. A failed/uncertain submission is paused and never retried. Startup pauses unresolved claimed/sent records for inspection and never replays them, while preserving valid authorization, its generation, counters and cooldown. Unclaimed queued messages remain queued; dispatch waits for the same context to attach and all normal gates to pass. A paused uncertain message is never automatically re-enrolled, even after reauthorization. Invalid saved authorization cancels queued work and requires deliberate human reauthorization. Missing legacy bound fields are treated as expired/exhausted, never as permission for unlimited work. Deleting a recipient cascades its policy/ledger; existing message provenance remains.

Browser API: `GET /api/sessions/{id}/inbox-delivery` returns policy, pending count, and up to 40 recent ledger records. `PUT` accepts `{enabled, requestId, deadline?, maxTurns?, unlimitedTurns?, cooldownSeconds, maxBatch}` (milliseconds UTC deadline). Omitted/null `deadline` means standing authorization. An enabled policy requires either `maxTurns:1..20` with `unlimitedTurns:false` (or omitted), or explicit `unlimitedTurns:true` with omitted/null `maxTurns`. Specifying both an unlimited choice and a finite cap is rejected. GET returns null for standing `deadline` or uncapped `maxTurns`. Cooldown and batch size remain required. Disable only needs `{enabled:false, requestId}`. Browser controls live in `web/inbox-delivery.js`, with readable wrapping, labels, status announcement, and 44px controls on phones. The existing same-user/browser trust boundary documented in AGENT-COMMUNICATION.md applies; this is not isolation against a malicious same-OS-user process.

Focused ownership review (2026-10-18): historical claimed/sent rows and reason strings were unsafe evidence of the active turn. The fix persists an exact `inbox_turn` token (request ID, generation, native context ID) in session state and carries it in `InboxPrompt` / `CancelInbox` commands. The runtime independently matches cancellation against its local active token; idle, human, other-request, other-generation and other-native turns ignore a late targeted cancellation. Terminal lifecycle status and ordinary human/initial prompt admission clear ownership. Native admission rechecks ownership and rejects revocation before the queued command reaches the native RPC. Exact completion clears only its own token and ledger batch; stale callbacks and human completions cannot touch another turn or its quota state. A fast completion closes its claimed batch before submit bookkeeping can run, and conditional bookkeeping cannot reopen it.

Finish/claim/event-write failure tests inject SQLite failures. The process latches admission closed, issues only an exact targeted cancellation, and persists paused ledger/policy state where writes remain possible. When storage is entirely unavailable, the already durable claim is retained and startup never replays it. Restore clears quota timers bound to a persisted inbox owner while retaining quota policy/evidence; unrelated human quota schedules are preserved. Project deletion serializes communication → run → workspace, and releases store/catalog guards before session/revocation callbacks. Reassignment releases catalog before callbacks. Completion reports commit and drop their store guard before interrupting an exact active owner. Concurrent finish versus reassign/delete/completion tests exercise these paths with a five-second failure bound. Schema version remains 7; this review adds only a backward-compatible session JSON ownership field.
